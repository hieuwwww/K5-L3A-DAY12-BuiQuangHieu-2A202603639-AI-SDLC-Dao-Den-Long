# TICKET-04 — Bình minh: web release v1.0.0 (approved design)

## Purpose and boundaries

Turn the existing Three.js web game into a reproducible, accessible v1.0.0 release. Preserve the 60 Hz simulation, all Phase 1–3 gameplay/headless behavior and all v1.2 JSONL fields/events; v1.3 adds release commands and non-gameplay facilities. User approved the browser benchmark and server-backed leaderboard on 2026-11-20. No fabricated hardware performance claims, video, cost totals, GitHub publication or passing grades.

## Approaches

- **Chosen on 2026-11-20: automated Chromium over the real web renderer.** A Node CLI launches a local web server and a windowed 1280×720 Chromium browser, opens a dedicated benchmark route/mode and captures frame timings from its `requestAnimationFrame` loop. Reuses existing Three.js assets and lighting. It measures the web build actually submitted. The browser compositor may cap FPS at display refresh; report `vsync_off:false` unless it is demonstrably disabled, and describe the limit in README. Browser RSS may not be measurable reliably across machines; use `peak_mem_mb:null` with a README explanation rather than claiming Node's RSS is the renderer's.
- **Rejected: desktop wrapper/Electron.** Easier native RSS/window control, but changes delivery/runtime and may yield different benchmark performance from the web game the grader will play.
- **Rejected: headless-only benchmark.** The existing `npm run benchmark` measures simulation speed, not graphics FPS/load time, and cannot satisfy the ticket.

## Benchmark and measurement

- `game.contract.json` v1.3 adds executable `bench_cmd` and `soak_cmd` strings; keep existing `headless_cmd` and normalized tuning unchanged. Suggested `node scripts/bench-web.js` and `node scripts/soak.js`; `npm run benchmark` remains available but clearly distinct if retained.
- The web benchmark mode creates the same Night 1 island/character/lighting/effects, with exactly 200 seeded wander shades spread evenly on the island, 100 seeded motes, L1–L3 lit at fuel 100 and Mây stationary at the origin. Do not rely on gameplay spawn caps. A benchmark-only simulation option (separate from scenario/player input) disables spawning, hits, pickup, fuel loss and end-of-night; shade wander remains live and follows the same simulation AI. Decorative character additions are disabled in benchmark and soak, or proven not to affect measurements. The mode must never appear in ordinary gameplay/headless output.
- Fly camera from `(30,15,0)` counterclockwise when viewed from above with one 15-second orbit; look at origin. Camera position derives from elapsed monotonic time rather than frame count. Keep 1280×720 windowed; browser CSS viewport and outer window sizing are measured and documented separately so the *render area* is exactly 1280×720.
- From process launch record monotonic start; `load_ms` ends at the first actual rendered bench frame. Warm up for three seconds, then take precisely `--duration` seconds of frame timestamps, excluding the warmup/boundary partial frame. Compute `frames`, `avg_fps=1000N/sum(dt)`, `p1_low_fps` from the largest `max(1,ceil(.01N))` deltas, and p95 frame milliseconds by a documented nearest-rank rule. Validate duration/seed and errors; exit zero only after writing JSON. Include renderer name/version, platform and honest `vsync_off`/`peak_mem_mb` values; grader thresholds are hardware-dependent and own run is informational only. Browser CLI dependency and reproducible install documented.

## Soak

- Run ten sequential nights in **one Node process** (`1→2→3` cyclic), night `i` with seed `7+i` (choose i=0-based; document this explicitly). A separate deterministic PRNG for input, seeded per night, reselects movement every 30 sim ticks; per tick independently samples jump 5%, dash 3%, pulse 2%, interact 10%. No pause. Each night runs until game end or standard duration. After night ten release reference to the last game and record RSS after reset; record starting RSS immediately after creating first night. Report results of all 10 nights, crashes, duration and RSS. Input generator and night lifecycle must be testable without browser or changing headless v1.2 JSONL. A failure should still produce failure evidence and nonzero exit; don't invent zero crashes.
- Because RSS depends on runtime allocator, test memory growth on the same-process CLI and report actual values without pretending a local run proves the 1.2 ratio on a different machine.

## Leaderboard and accessibility

- **Approved persistence choice:** a local JSON file shared through a small same-origin Node server API; normal browser writes and `npm start -- --export-leaderboard out.json` export the identical durable entries. The server must restrict paths/inputs and use atomic file replacement; never expose arbitrary filesystem read. Name validates `[A-Za-z0-9_]{3,12}`; record `{name,score,nights_won,achieved_at,seed}` with ISO timestamp and stable order score descending/earliest achievement first (stable final insertion tie). Save after loss at any night or after winning Night 3; winners of nights 1–2 continue without save; main menu displays leaderboard. Derive score from won-night total only and carry seed through a run. Server-backed JSON means the release bundle includes its tiny server; merely opening static `index.html` does not persist scores or support CLI export.
- Persist keymap for four directions, jump, dash, interact, pulse, pause; detect duplicates before saving, restore defaults, and show the active bindings in HUD/help. Subtitles and visual cues for shade spawn (edge-of-screen directional pointer), wind warning, final 10 seconds and low fuel, without audio dependence. Maintain minimum 18px interface text at 1280×720 and optional 1.25× text. Reduced motion disables camera shake and full-screen flash without changing simulation/headless output. Browser-only settings persist and recover safely from malformed storage.

## Packaging, docs and evidence

- Use a checked-in distributable web folder generated by a build script (bundle Three.js rather than depending on a runtime `node_modules` import map). A downloadable release ZIP contains static assets plus small local Node server for leaderboard persistence and a README; release is runnable in at most three commands from a fresh clone. Update README with screenshot/GIF, supported Node/browser/graphics requirements, controls, start/tests/headless/bench/soak/export, `vsync_off` and web RSS caveat. Add Phase 1–4 changelog, complete asset/audio/AI tool credits and retain license. Test a fresh install/build and ZIP execution. `bench.json` and `soak.json` are generated from actual runs and committed; don't hand-edit measurements.
- Prepare 1–2 page retro citing available Phase 1–4 evidence, concrete AI errors and fixes and harness contributions. Token/cost figures must come from available usage records, otherwise mark a bounded estimate and its source, never assert precision. Capture a live <5 minute MP4 with gameplay and test/headless/bench evidence if recording is possible; else report blocker, not a placeholder video. GitHub public check, `phase-4` tag and Release `v1.0.0` occur only after release artifact and acceptance verification, without discarding uncommitted Phase 2/3 user work; inspect git status and release/tag conflicts before staging/publishing.

## Acceptance and risks

Run prior tests, v1.3 contract tests, browser smoke, real 30-second benchmark and 10-night soak, deterministic headless comparisons, fresh-clone/release smoke, `npm test`, `npm run verify`, `npm run benchmark`, `git diff --check`. Verify benchmark benchmark-only scene count/positions, camera path, event suppression, frame math and reproducibility. Verify leaderboard sorting/persistence/export and accessibility with keyboard/browser interaction. Hardware thresholds are determined on grader machine; report local results and any unmet requirement. Risks: lack of reliable browser RSS and vsync control, Chrome availability in clean clone, static-only persistence versus CLI export, and release/demo permissions or upload size.
